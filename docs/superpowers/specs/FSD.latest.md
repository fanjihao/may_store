## 0. PRD 概述

本章为产品视角的概要，定义产品愿景、用户、旅程、KPI、竞品、术语和 User Story，研发、SRE、运营、客服、法务、市场等团队均应阅读。

### 0.1 产品愿景

**一句话定位**：让"被记住的小事"成为两个人之间长期可感知的情感连接。

**长期愿景（3-5 年）**：

- 成为中文世界最被信任的"亲密关系 / 共同生活"协作工具。
- 通过"积分 + 心愿 + 履约"机制，把"对方为我做的事"沉淀为可量化的资产。
- 在不公开化、不社交化的前提下，让每一对固定关系的协作更可量化、更有仪式感。

**短期目标（1 年）**：

- 服务 10 万注册用户。
- 维持 7 日留存 ≥ 30%、30 日留存 ≥ 15%。
- 维持心愿完成率 ≥ 60%、订单完成率 ≥ 80%。
- 维持客诉率 ≤ 0.5%。

**我们不做什么**：

- 不做公开社区 / 广场。
- 不做陌生人匹配 / 相亲。
- 不做虚拟礼物打赏 / 直播打榜。
- 不做付费充值（仅预留看广告获取钻石能力）。

### 0.2 目标用户画像

#### 0.2.1 主画像：核心双人组（占比 70%）

- **关系类型**：稳定情侣、已婚夫妻、共同生活的伴侣。
- **年龄**：22-40 岁。
- **场景**：合租、异地（短距离通勤异地）、同住一套房。
- **数字化程度**：高，习惯用微信、抖音、小红书。
- **核心诉求**：
  - 把"日常关心"沉淀为可被回看的记录。
  - 让"被记住的小事"成为长期仪式。
  - 减少"被忽视感"、"做了没说"的怨气。
- **痛点**：
  - 微信聊天记录容易淹没、半年后无人翻看。
  - 家庭琐事（做饭、家务）付出不均，长期累积矛盾。
  - 异地时"今天为你做了什么"无法可视化。

#### 0.2.2 次画像 A：异地恋人（占比 15%）

- **关系类型**：异地恋（出差、留学、跨城工作）。
- **频率**：每周 1-2 次线下见面，平时以微信维系。
- **核心诉求**：线下见面的"事"被记录、被回看；远程也能"下单"、"打卡"。

#### 0.2.3 次画像 B：老夫老妻（占比 10%）

- **关系类型**：结婚 5 年以上的稳定关系。
- **场景**：家务分配、节假日仪式感。
- **核心诉求**：把"付出"显性化，避免"我没做"的口角。

#### 0.2.4 次画像 C：亲密室友 / 家人（占比 5%）

- **关系类型**：同住一房的闺蜜、合租朋友、亲属。
- **差异**：不是"恋爱关系"，但同样有协作需求。
- **本产品是否支持**：当前 FSD 以"双人组 + 互相服务"为模型，**官方不支持**第 3 方关系类型。

#### 0.2.5 不覆盖人群

- 单身用户。
- 临时关系 / 一次性用户。
- 公开社交需求强烈的用户。
- 商业用途（餐厅、B 端商家）。

### 0.3 用户旅程图

#### 0.3.1 旅程 A：首次注册到首单

```text
[注册] → [创建组 / 受邀加入] → [设置角色] → [上传菜品] → [下单] → [接单] → [完成] → [确认] → [获得积分] → [通知推送]
```

- **关键节点**：
  - T0 注册：30 秒内必须完成。
  - T0+1min 创建组：默认 Buyer，另一成员 Seller。
  - T0+5min 上传菜品：Seller 录入 3-5 个家常菜。
  - T0+30min 首单：Buyer 下单，触发 WebSocket 通知 Seller。
  - T0+2h 完成：Seller 标记完成。
  - T0+2.5h 确认：Buyer 确认，积分入账。
- **异常分支**：
  - Seller 拒单 → Buyer 可重选时间或关闭。
  - 超时未接单 → 自动 TIMEOUT 状态。

#### 0.3.2 旅程 B：心愿全周期

```text
[创建心愿] → [协商积分] → [协商期限] → [双方确认] → [入池] → [攒积分] → [选择 + 冻结] → [履约] → [打卡] → [扣减积分] → [质量评价]
```

- **典型时长**：1-30 天，跨多个订单完成。
- **关键节点**：
  - 双方确认（CREATED）：FSD 状态机入口。
  - 选择并冻结（CLAIMED）：积分从可用转入冻结。
  - 履约打卡（FINISHED）：冻结转正式扣减。
- **异常分支**：
  - 履约逾期 → EXPIRED + 退还积分。
  - 协商破裂 → CLOSED + 退还冻结积分。
  - 协商中任一方拒绝 → reject 关闭。

#### 0.3.3 旅程 C：做客场景

```text
[受邀做客] → [主人家菜单] → [选择菜品] → [下单 + 备注] → [主人家 Seller 完成] → [主人家 Seller 获得积分] → [做客人仅查看状态]
```

- **做客人积分**：做客用户**不**获得主人家组的积分。
- **防刷**：同一做客用户对同一主人家每日 ≤ 1 单（可配置）。

#### 0.3.4 旅程 D：角色互换

```text
[检查无在途订单/心愿] → [调用 swap-role] → [历史角色保留] → [后续按新角色协作]
```

- **关键约束**：互换不改变心愿的 `requester_id` / `fulfiller_id`。

#### 0.3.5 旅程 E：异常 / 申诉

```text
[用户反馈问题] → [客服 / 反馈入口] → [管理员审核] → [审计日志] → [必要时补偿流水]
```

### 0.4 核心 KPI 与北极星指标

#### 0.4.1 北极星指标（North Star Metric）

**双人组日均心愿完成数**（Group Daily Finished Wishes）

- 含义：每个双人组每天完成的心愿数。
- 计算：`sum(wishes.status=FINISHED created today) / active_group_count_today`。
- 目标：MVP 阶段 ≥ 0.1，V1.0 阶段 ≥ 0.3。
- 选择理由：心愿完成是"双向付出 + 双方确认 + 长期沉淀"的最高表达，牵引所有指标。

#### 0.4.2 业务指标（必看）

| 指标                          | 公式                                                          | 目标          | 测量频率 |
| ----------------------------- | ------------------------------------------------------------- | ------------- | -------- |
| DAU                           | `count(distinct user_id) where last_active_date = today`     | 1.5-3 万      | 日       |
| 次日 / 7 日 / 30 日留存       | `D1/D7/D30 retention`                                         | 40% / 30% / 15% | 日       |
| 注册转化率                    | `signup_count / landing_uv`                                   | ≥ 30%         | 周       |
| 每组日均订单数                | `sum(orders where group_id) / active_group_count_today`       | ≥ 0.5         | 日       |
| 订单完成率                    | `sum(CONFIRMED_COMPLETED) / sum(CREATED)`                     | ≥ 80%         | 日       |
| 心愿入池率                    | `sum(CREATED wishes) / sum(wishes)`                          | ≥ 70%         | 周       |
| 心愿完成率                    | `sum(FINISHED wishes) / sum(CREATED wishes)`                  | ≥ 60%         | 周       |
| 角色互换频率                  | `sum(RoleSwappedEvent) / active_group_count`                  | ≥ 0.2 次/月   | 月       |
| 签到率                        | `signed_user_count / active_user_count_today`                 | ≥ 50%         | 日       |
| 客诉率                        | `support_ticket_count / DAU`                                  | ≤ 0.5%        | 周       |

#### 0.4.3 质量指标

| 指标                      | 目标      | 测量方式             |
| ------------------------- | --------- | -------------------- |
| API 月度可用性            | ≥ 99.9%   | 月度统计             |
| 核心写接口 P95            | ≤ 300ms   | Prometheus 监控      |
| 核心读接口 P95            | ≤ 200ms   | Prometheus 监控      |
| 5xx 错误率                | ≤ 0.2%    | 5 分钟粒度           |
| 事件消费 P95 延迟         | ≤ 30s     | event_log processed_at |
| 经济对账一致率            | 100%      | 每日对账任务         |
| WebSocket 断连率          | ≤ 5%/小时 | 连接数-建立数        |

#### 0.4.4 反指标（不能涨的指标）

- 投诉率、退款率、刷分订单占比、做客订单刷分率、僵尸组占比、订单超时率。

### 0.5 竞品分析

#### 0.5.1 直接竞品：情侣 / 夫妻协作 App

| 产品       | 定位                | 核心机制               | 我们的差异                                  |
| ---------- | ------------------- | ---------------------- | ------------------------------------------- |
| 微爱       | 情侣纪念日 + 树      | 纪念日、时光树         | 缺经济 / 履约机制；偏静态内容               |
| 小恩爱     | 情侣空间 + 计时      | 位置共享、纪念日       | 偏社交 / 监控；缺长期协作沉淀               |
| 恋爱记     | 情侣日记             | 日记、纪念日           | 偏日记；缺双向经济机制                      |
| Couples    | 海外情侣 App         | 日历、纪念日           | 缺中文 + 缺经济机制                         |

**我们的差异**：把"对方为我做的事"通过订单 + 积分 + 心愿机制量化；不靠社交压力，靠"履约 + 打卡"完成闭环。

#### 0.5.2 间接竞品：家庭 / 协作类

| 产品       | 定位                | 核心机制               | 我们的差异                                  |
| ---------- | ------------------- | ---------------------- | ------------------------------------------- |
| OurHome    | 家庭家务分配        | 任务 + 积分            | 家庭多人 vs 我们固定双人；无心愿履约        |
| TickTick   | 待办                | 任务 + 协作            | 偏工具；无情感沉淀                          |
| 滴答清单   | 待办                | 任务 + 习惯            | 同上                                        |

**我们的差异**：固定双人关系 + 积分经济 + 履约打卡，区别于通用协作工具。

#### 0.5.3 我们的护城河

- **双人关系建模**：所有机制为"固定 2 人"设计，不是多人协作。
- **积分经济闭环**：订单 → 积分 → 心愿 → 履约 → 扣减。
- **自然人绑定**：履约人与 user_id 绑定，角色切换不改责任。
- **私密性**：无公开广场、无陌生人社交。

#### 0.5.4 风险与机会

- **风险**：情侣 App 用户流失快（关系结束 = App 卸载）；我们需通过"长期沉淀"对抗。
- **机会**：从"情侣"扩展到"亲密关系 / 同居"；不靠公开社交，靠经济闭环建立切换成本。

### 0.7 User Story 库

> 格式：作为 [角色]，我希望 [能力]，以便 [业务价值]。

#### 0.7.1 账号与组

- **US-01**（Buyer）作为新用户，我希望通过微信一键登录，以便 30 秒内进入产品。
- **US-02**（Buyer）作为登录用户，我希望创建双人组并生成邀请码，以便邀请另一半加入。
- **US-03**（受邀人）作为收到邀请的另一半，我希望通过邀请码加入组，以便进入同一协作空间。
- **US-04**（组员）作为组内成员，我希望查看双方的角色和积分余额，以便了解当前状态。
- **US-05**（组员）作为组内成员，我希望在无在途订单/心愿时互换角色，以便切换主被动。
- **US-06**（组员）作为组内成员，我希望退出前看到"结清检查"摘要，以便了解待处理事项。

#### 0.7.2 订单

- **US-10**（Buyer）作为下单人，我希望从菜品库选菜并下单，以便 Seller 接单。
- **US-11**（Seller）作为接单人，我希望实时收到新订单通知（WebSocket），以便及时接单。
- **US-12**（Seller）作为接单人，我希望接单后明确截止时间，以便规划履约。
- **US-13**（Seller）作为接单人，我希望完成时填写备注，以便 Buyer 知道进度。
- **US-14**（Buyer）作为下单人，我希望确认完成后 Seller 获得积分，以便激励履约。
- **US-15**（Buyer）作为下单人，我希望订单未完成时确认不发放积分，以便维护公平。
- **US-16**（Buyer 或 Seller）作为任一方，我希望在 CREATED/ACCEPTED 状态取消订单，以便调整计划。
- **US-17**（做客人）作为受邀做客的好友，我希望在主人家厨房看菜单并下单，以便点菜。
- **US-18**（做客人）作为受邀做客的好友，我希望加备注（口味/忌口/到访时间），以便主人家准备。

#### 0.7.3 积分与经济

- **US-20**（Seller）作为接单人，我希望看到今日已获积分和剩余上限，以便避免无效下单。
- **US-21**（Buyer）作为下单人，我希望超额订单仍能完成但不发积分，以便不浪费履约。
- **US-22**（组员）作为任意一方，我希望查看积分流水（含余额前后），以便对账。
- **US-23**（组员）作为任意一方，我希望查询组钻石余额和流水，以便规划扩容。
- **US-24**（组员）作为任意一方，我希望查看组经验和当前等级进度，以便了解升级节奏。

#### 0.7.4 心愿

- **US-30**（Requester）作为心愿创建者，我希望发起心愿并设置初始报价，以便开始协商。
- **US-31**（任一方）作为任一协商方，我希望在 DRAFT/NEGOTIATING 状态报价/反报价/修改期限，以便达成一致。

## 1. 产品定位与范围

### 1.1 产品定位

心愿菜单是一款面向固定双人关系的组内协作产品。产品围绕“菜单/订单/心愿/积分/经验/等级/钻石/足迹”形成闭环：一方下单，一方接单完成并获得个人爱心积分，同时小组获得经验；积分可用于选择本组心愿；对方履约后由发起人打卡反馈，管理员可按反馈质量向组发放额外钻石奖励；组等级提升可扩大每日积分和经验上限。

产品核心不是公开社区，也不是泛任务平台，而是服务固定双人组内的长期互动。

### 1.2 核心边界

- 仅面向固定双人组：同一小组固定 2 人。
- 同一时刻每组只有 1 个 Buyer 和 1 个 Seller。
- 角色可互换，但历史数据绑定操作时的用户 ID，角色切换不改写历史。
- 用户可以拥有自己的长期账号，并可加入或拥有自己的组；做客好友不是一次性匿名用户。
- 无公开广场，足迹、心愿、订单、菜品均仅组内可见。
- 后端技术选型暂定 Rust + PostgreSQL 不变。
- 10 万用户目标指注册用户。
- 暂不做钻石充值；因资质原因，仅预留看广告获取钻石能力。

### 1.3 核心资产

| 资产                  | 归属        | 用途                              | 限制                               |
| --------------------- | ----------- | --------------------------------- | ---------------------------------- |
| 爱心积分 `love_point` | 用户 + 小组 | 本组心愿选择                      | 跨组不可使用，不可提现，不可转账   |
| 组钻石 `diamond`      | 小组        | 扩容、解锁能力、运营奖励          | 暂不支持充值，预留广告获取         |
| 组经验 `group_exp`    | 小组        | 组等级升级，扩大每日积分/经验上限 | 仅通过订单、活动等后台配置来源获取 |

### 1.4 阶段目标

| 阶段 | 目标               | 必须交付                                                             | 暂缓交付                  |
| ---- | ------------------ | -------------------------------------------------------------------- | ------------------------- |
| MVP  | 支撑真实双人组使用 | 微信登录、双人组、角色、菜品、订单、爱心积分、心愿、签到、通知、上传 | AI 推荐、商业化、公开内容 |
| Beta | 支撑 1 万注册用户  | 管理后台、审核、监控告警、灰度配置、数据看板、压测                   | 多区域部署、复杂活动      |
| V1.0 | 支撑 10 万注册用户 | 高可用部署、备份恢复、风控、审计、隐私合规、上线验收                 | 付费充值、公开广场        |

## 2. 用户、组与角色模型

### 2.1 用户账号

用户必须是长期账号。微信小程序登录以微信 `openid` 绑定用户，后续可扩展手机号登录。客人也使用自己的账号，并可拥有自己的小组。

### 2.2 双人组

- 每个 `association_group` 固定 2 名正式成员。
- 组内数据与其他组严格隔离。
- 组内保存当前角色映射：`buyer_user_id`、`seller_user_id`。
- 用户跨多个组时，爱心积分按 `user_id + group_id` 独立计算。

### 2.3 角色权限

| 角色          | 权限范围                                                     | 积分获取规则                                                                     |
| ------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| Buyer 下单人  | 创建本组订单；参与心愿协商；浏览心愿池；有积分时可选择心愿   | 订单无任何积分入账；想获得积分必须切换为 Seller                                  |
| Seller 接单人 | 接单并完成本组订单或做客订单；参与心愿协商；消耗积分选择心愿 | 完成本组订单或主人家做客订单后，系统按后台规则自动发放爱心积分，并为小组增加经验 |

### 2.4 角色互换

默认前置条件：

- 小组无未完结在途订单。
- 操作人无 `CLAIMED` 状态且自己作为发起人或履约人的在途心愿。
- 互换后当前 Buyer 与 Seller 对调。
- 历史订单、心愿、积分流水均保留操作时用户 ID 和当时角色快照。

配置开关：

| 配置项                     | 默认值  | 说明                                                                 |
| -------------------------- | ------- | -------------------------------------------------------------------- |
| `swap_ignore_ongoing_wish` | `false` | 为 `true` 时，允许带在途心愿互换身份；已选择心愿的发起人和履约人不变 |

### 2.5 做客关系

- 做客用户必须使用长期账号。
- 做客用户通过邀请链接直接访问主人家厨房。
- 做客用户可查看主人家厨房菜单、选择菜品、下单、标记订单偏好或备注。
- 做客订单归属主人家小组，由主人家 Seller 完成。
- 做客订单与做客用户自己的组数据隔离，但订单列表需要同时展示“自己组订单”和“我发起的做客订单”。
- 做客用户仅可查看邀请授权范围内的主人家菜单、自己创建的做客订单以及必要的订单状态。
- 做客订单完成后，主人家 Seller 可获得爱心积分；做客用户不获得主人组爱心积分。
- 做客订单积分必须接入风控，避免通过邀请链接刷单刷积分。

## 3. 总体架构

### 3.1 分层架构

- API 层：RESTful API、WebSocket、参数校验、认证授权、错误码。
- 应用层：业务用例编排、事务边界、幂等、领域事件发布。
- 领域层：订单状态机、心愿状态机、经济规则、角色互换、成就规则。
- 事件层：事件定义、事件日志、Worker 消费、重试、死信。
- 基础设施层：PostgreSQL、Redis、对象存储、微信接口、广告接口、内容审核。

### 3.2 模块划分

| 模块           | 职责                                       |
| -------------- | ------------------------------------------ |
| `user`         | 用户、登录、账号状态、黑名单               |
| `group`        | 双人组、成员、角色映射、邀请               |
| `food`         | 菜品、标签、食材、图片、步骤               |
| `order`        | 订单、状态机、评价、催办、附件             |
| `wish`         | 心愿创建、协商、兑换、冻结积分、打卡、审核 |
| `economy`      | 爱心积分、组钻石、流水、对账               |
| `sign_in`      | 签到、连续签到、组钻石奖励                 |
| `footprint`    | 组内足迹、纪念内容、图片                   |
| `achievement`  | 成就规则、成就墙、事件判定                 |
| `notification` | 系统通知、订单通知、心愿通知、未读数       |
| `upload`       | 文件上传令牌（七牛云直传）、内容审核       |
| `admin`        | 后台配置、审核、用户管理、数据统计         |
| `event`        | 事件日志、Worker、幂等处理                 |
| `ws`           | WebSocket 实时通知                         |
| `dashboard`    | 组内看板、运营看板、指标聚合               |

### 3.3 核心原则

- 所有经济变动必须写流水，禁止直接改余额。
- 订单状态、心愿状态、积分冻结/扣减必须具备状态机约束。
- 写接口必须支持幂等。
- 所有组内资源必须校验 `group_id` 和成员关系。
- 异步联动通过事件驱动，避免模块间强耦合。
- 所有关键操作保留审计字段和 trace_id。

## 4. 登录、邀请与权限

### 4.1 微信登录流程

1. 前端调用 `uni.login()` 或微信小程序登录接口获取 `code`。
2. 前端请求 `POST /api/auth/wechat-login`。
3. 后端使用 `code` 调用微信接口换取 `openid` 和 `session_key`。
4. 后端按 `openid` 查找用户。
5. 已存在用户返回访问令牌、刷新令牌和用户信息。
6. 不存在用户创建账号或进入补充资料流程。

安全要求：

- 前端不得直接传入可信 `openid` 创建正式用户。
- 日志中禁止记录 `code`、`session_key`、JWT、手机号明文。
- JWT 使用短有效期访问令牌 + 可撤销刷新令牌。

### 4.2 组邀请

- 组内成员可以生成邀请链接或邀请码。
- 受邀用户登录后加入组。
- 若组已满 2 人，邀请失效。
- 邀请码必须设置有效期和使用次数，不提供主动撤销端点，到期或达上限后自动失效。
- **仅 Seller 角色可创建邀请**（Buyer 不能发起邀请）。
- **每个用户最多拥有 5 个 ACTIVE 状态的小组**，超出后需先退出旧组才能加入新组。

### 4.3 权限校验

所有资源接口必须校验：

- 用户是否登录且状态正常。
- 用户是否属于当前组。
- 当前组是否为资源所属组。
- 当前用户角色是否有权执行操作。
- 做客用户是否拥有该邀请授权范围。

## 6. 订单系统

### 6.1 订单类型

| 类型     | 说明                                                                     |
| -------- | ------------------------------------------------------------------------ |
| `NORMAL` | 组内普通订单                                                             |
| `GUEST`  | 做客订单，由受邀好友通过邀请链接访问主人家厨房后创建，主人组 Seller 完成 |

### 6.2 订单状态机

```text
CREATED
  -> ACCEPTED
  -> PRODUCTION_COMPLETED
  -> CONFIRMED_COMPLETED
  -> CONFIRMED_INCOMPLETE

CREATED -> REJECTED
CREATED -> CANCELLED
CREATED/ACCEPTED -> TIMEOUT
ACCEPTED -> CANCELLED
```

- Buyer 或 Seller 在 `CREATED` 或 `ACCEPTED` 状态都可发起取消，双方任一操作生效。
- 取消由系统定时任务（超时）或管理员触发 `TIMEOUT` 状态。
- `REJECTED` 仅由 Seller 在 `CREATED` 状态发起（明确拒绝）。

### 6.3 积分发放规则

- 仅 Seller 完成订单后获得爱心积分。
- Buyer 创建或确认本组订单不获得爱心积分。
- 做客订单由主人家 Seller 完成后，给主人家 Seller 发放爱心积分。
- 做客用户不获得主人组爱心积分，也不能消耗主人组爱心积分。
- 订单积分规则全部由管理员在后台配置，用户侧不可配置订单积分。
- 可按订单类型配置不同积分：`NORMAL` 和 `GUEST` 可分别配置默认值、上限、每日计分次数。
- 每个用户每天在每个组内有爱心积分获取上限；超过上限后，订单仍可完成，但不再增加爱心积分。
- 每个组每天有经验获取上限；超过上限后，订单仍可完成，但不再增加组经验。
- 组等级提升后可扩大每日爱心积分上限和每日经验上限，具体等级经验和上限由管理员后台配置。
- 订单确认完成后，未超上限的爱心积分写入 `love_point_transactions`。
- 订单确认完成后，未超上限的组经验写入 `group_exp_transactions`。
- 重复确认、重复事件消费不得重复发放爱心积分和组经验。

### 6.4 做客订单列表与标记

- 用户订单列表需要聚合展示两类订单：自己所属组订单、自己发起的做客订单。
- 做客订单需标记主人家信息、订单类型 `GUEST`、当前状态和完成方。
- 做客用户可对自己发起的做客订单添加备注或标记，例如口味偏好、忌口、到访时间。
- 主人家组内列表需要展示做客订单，并区分普通订单与做客订单。
- 做客订单只允许创建人、主人家组内 2 人和管理员查看。

### 6.5 订单防刷积分与经验

- 所有订单发放爱心积分和组经验前必须通过风控校验，不仅限于做客订单。
- 防刷的第一层规则是每日上限：用户每日爱心积分上限、组每日经验上限、订单类型每日计分次数上限。
- 超出每日上限的订单仍可正常完成、评价、生成足迹，但 `point_grant_status=REJECTED_LIMIT`，不增加爱心积分；`exp_grant_status=REJECTED_LIMIT`，不增加组经验。
- 同一做客用户对同一主人家小组每日可计分做客订单数量默认不超过 1 单。
- 同一邀请链接每日可计分订单数量、总计分订单数量需要后台可配置。
- 同一设备、同一 IP、同一微信账号、同一主人家小组短时间内大量创建做客订单时进入风险状态。
- 风险订单可正常流转，但积分和经验发放进入 `PENDING_REVIEW` 或不计分，等待管理员审核。
- 被判定为刷分的订单不发放爱心积分和组经验；已发放的需要通过补偿流水扣回。
- 风控结果、命中规则、处理人和处理时间必须写入审计日志。

### 6.6 并发安全

- 接单使用条件更新：仅 `CREATED` 状态可接单。
- 完成、确认、取消、超时均必须校验当前状态。
- 关键写接口使用 `Idempotency-Key`。
- 订单积分发放以 `order_id + event_type` 作为幂等键。

## 7. 心愿系统

### 7.1 业务目标

心愿系统用于把“双人之间想要对方完成的事情”沉淀为组内心愿池。用户 A 创建心愿，双方协商爱心积分价格和履约期限，双方线上确认后进入心愿池。A 通过完成 B 的菜品订单获取爱心积分，攒够后选择该心愿并冻结积分；随后 B 必须在约定期限内线下履约；A 完成打卡反馈后，心愿完成，积分正式扣除。管理员只对打卡质量进行后台查看，并可发放额外组钻石奖励。

### 7.2 数据隔离与资产规则

- 心愿归属小组，仅组内 2 人可查看和操作。
- 爱心积分绑定 `user_id + group_id`，跨组不可使用。
- 爱心积分仅用于本组心愿选择，不可提现、不可转账。
- 心愿选择使用冻结机制，打卡反馈完成后才正式扣减。
- 履约人与自然人用户 ID 绑定，与当前 Buyer/Seller 角色无关。
- 角色互换不改变已选择心愿的履约人、选择人和历史责任。

### 7.3 心愿角色与自然人职责

心愿流程以自然人用户为核心，不以当前角色为最终责任主体。创建心愿时的发起人记为 `requester_id`，对方自然人记为 `fulfiller_id`。

| 操作                     | 发起人 requester | 履约人 fulfiller | 管理员 |
| ------------------------ | ---------------- | ---------------- | ------ |
| 创建心愿                 | 是               | 否               | 否     |
| 协商积分价格             | 是               | 是               | 否     |
| 协商履约期限             | 是               | 是               | 否     |
| 线上确认                 | 是               | 是               | 否     |
| 选择心愿并冻结积分       | 是               | 否               | 否     |
| 线下履约                 | 否               | 是               | 否     |
| 打卡反馈                 | 是               | 否               | 否     |
| 查看履约质量并发额外钻石 | 否               | 否               | 是     |

### 7.4 整体业务流程

```text
A 创建心愿
  -> DRAFT
  -> 双方协商积分价格 + 履约期限
  -> 双方线上确认
  -> CREATED 进入组内心愿池

A 通过完成 B 的菜品订单获取爱心积分
  -> 受每日积分上限限制
  -> 完成订单同时获取组经验
  -> 受每日经验上限限制
  -> 组等级提升可扩大每日积分/经验上限

A 攒够积分
  -> 选择该心愿
  -> 冻结 A 的爱心积分
  -> CLAIMED，绑定履约人 B，生成履约截止时间

B 在期限内线下履约
  -> A 提交打卡反馈
  -> FINISHED，正式扣除 A 的冻结积分
  -> 管理员后台查看质量，可额外发放组钻石

B 逾期未履约
  -> EXPIRED
  -> 退还 A 的冻结积分
  -> 记录 B 的逾期履约记录
  -> 心愿按配置回池或关闭

任意非终态
  -> 双方协商一致关闭 -> CLOSED
```

### 7.5 状态定义

| 状态          | 说明                             | 可操作                           |
| ------------- | -------------------------------- | -------------------------------- |
| `DRAFT`       | 发起人创建草稿                   | 进入协商、关闭                   |
| `NEGOTIATING` | 双方协商积分和履约期限           | 报价、还价、修改期限、确认、关闭 |
| `CREATED`     | 双方已确认，进入组内心愿池       | 选择心愿、关闭                   |
| `CLAIMED`     | 发起人已选择，积分已冻结，待履约 | 打卡反馈、逾期处理、关闭         |
| `FINISHED`    | 已履约并打卡，积分正式扣减       | 终态，管理员可追加钻石奖励       |
| `EXPIRED`     | 履约人逾期未履约，积分已退还     | 终态或按配置回到 `CREATED`       |
| `CLOSED`      | 双方关闭或作废                   | 终态                             |

### 7.6 关键业务规则

- 任一组内成员都可以创建心愿；创建后发起人为 `requester_id`，另一名组成员为默认 `fulfiller_id`。
- 双方必须线上确认积分价格和履约期限，心愿才可进入 `CREATED`。
- 双方确认前，任何一方可调用 `reject` 关闭整个协商；协商中的报价、期限不需要单独的"取消确认"操作，通过 reject 即可中止。
- `CREATED` 状态才可被发起人选择。
- 选择心愿时检查发起人爱心积分余额，余额不足拒绝。
- 选择心愿时冻结发起人的爱心积分，不立即扣减。
- 同一心愿同一时间只能有一次有效选择。
- `CLAIMED` 生成履约截止时间，截止时间来自双方协商的履约期限。
- 履约人必须在期限内线下履约；系统以发起人打卡反馈作为履约完成证明。
- 发起人提交打卡反馈后，冻结积分转正式扣减，心愿进入 `FINISHED`。
- 管理员不负责判定心愿是否完成，只查看反馈质量并决定是否额外发放组钻石。
- 履约逾期时退还冻结积分，记录履约人的逾期履约记录。
- 每个用户需要展示其作为履约人时的履约率、逾期次数、平均履约时长等信息，组内双方可见。
- 用户退出组前必须结清：不能存在自己作为发起人或履约人的未完结心愿、冻结积分、待履约记录。

### 7.7 积分冻结与扣减

| 阶段           | 积分动作                                             |
| -------------- | ---------------------------------------------------- |
| 创建/协商/入池 | 无积分变动                                           |
| 选择心愿       | 生成冻结流水，增加 `frozen_love_point`，减少可用余额 |
| 履约中         | 无积分变动                                           |
| 打卡反馈完成   | 冻结转正式扣减，生成扣减流水                         |
| 履约逾期       | 解冻退回，生成解冻流水                               |
| 关闭           | 如存在冻结积分，必须解冻                             |

### 7.8 履约率与退出结清

履约统计按自然人和小组维度计算，和当前角色无关。

| 指标                        | 说明                 |
| --------------------------- | -------------------- |
| `fulfillment_total`         | 作为履约人的总心愿数 |
| `fulfillment_finished`      | 按期完成数量         |
| `fulfillment_expired`       | 逾期数量             |
| `fulfillment_rate`          | 按期完成率           |
| `avg_fulfillment_hours`     | 平均履约时长         |
| `pending_fulfillment_count` | 当前待履约数量       |

退出组前必须满足：

- 无自己发起且未完结的心愿。
- 无自己作为履约人且未完结的心愿。
- 无本组冻结爱心积分。
- 无待处理的逾期补偿或管理员钻石奖励。

### 7.9 管理员质量奖励

管理员查看打卡反馈后，可根据质量发放额外组钻石奖励。

| 字段                  | 说明                                  |
| --------------------- | ------------------------------------- |
| `quality_reviewer_id` | 查看/奖励管理员                       |
| `quality_level`       | `NONE`、`NORMAL`、`GOOD`、`EXCELLENT` |
| `quality_remark`      | 质量备注                              |
| `diamond_reward`      | 本次额外发放钻石                      |
| `quality_reviewed_at` | 查看时间                              |

要求：

- 钻石奖励必须走 `diamond_transactions`。
- 同一心愿额外钻石奖励必须幂等。
- 可配置质量等级对应钻石、单次钻石上限和管理员单日发放上限。
- 未发钻石时也可记录已查看质量，便于运营统计。

### 7.10 心愿事件

## 8. 经济系统

### 8.1 爱心积分 love_point

- 归属：用户 + 小组。
- 来源：Seller 完成本组订单或主人家做客订单。
- 用途：兑换本组心愿。
- 限制：不可提现、不可转账、不可跨组使用。
- 余额模型：可用余额 + 冻结余额。
- 获取限制：按用户 + 小组 + 自然日计算每日获取上限，超出后订单完成不再增加爱心积分。

### 8.2 组钻石 diamond

- 归属：小组。
- 来源：签到奖励、心愿质量奖励、运营补偿、预留广告奖励。
- 用途：足迹容量扩展、菜品/标签容量扩展、玩法解锁。
- 暂不支持充值。

### 8.3 组经验 group_exp

- 归属：小组。
- 来源：完成本组普通订单、主人家做客订单、活动等后台配置来源。
- 用途：提升组等级。
- 获取限制：按小组 + 自然日计算每日经验上限，超出后订单完成不再增加组经验。
- 等级作用：组等级提升后，可扩大每日爱心积分上限、每日经验上限、容量上限或其他玩法能力。
- 等级经验表、每日上限、订单经验值全部由管理员后台配置。

### 8.4 流水规则

所有变动必须写流水：

- `love_point_transactions`
- `diamond_transactions`
- `group_exp_transactions`

流水必须包含：

- `user_id` 或 `group_id`
- `amount`
- `balance_before`
- `balance_after`
- `frozen_before`
- `frozen_after`
- `biz_type`
- `biz_id`
- `idempotency_key`
- `trace_id`
- `created_at`

### 8.5 对账

- 每日任务聚合流水，与余额快照比对。
- 发现不一致时告警并生成修复任务。
- 经济修复必须走补偿流水，不允许后台直接改余额。

## 9. 签到、足迹与成就

### 9.1 签到

- 签到奖励发放组钻石。
- 同一天同一用户同一组只能签到一次。
- 双方当日均签到时可触发额外组钻石奖励。
- 签到按用户本地时区计算连续天数，但数据库统一 UTC 存储。

### 9.2 足迹

- 足迹仅组内可见，无公开广场。
- 订单完成、心愿完成后可生成纪念足迹。
- 用户可上传文字、图片和可选位置。
- 位置默认可选，用户可选择不展示位置。
- 图片需通过内容安全审核。

### 9.3 成就

- 成就由事件驱动异步判定。
- 支持用户成就和组成就。
- 成就规则通过配置表管理。
- 成就解锁必须幂等。

## 10. 通知与 WebSocket

### 10.1 通知类型

通知类型共 4 类，与 API `notification.type` 字段一致：

| 类型     | 场景                                                  |
| -------- | ----------------------------------------------------- |
| 订单通知 | 订单创建、接单、完成、确认、超时                      |
| 心愿通知 | 心愿协商、入池、兑换、打卡、审核                      |
| 签到通知 | 签到成功、连续天数提醒、双方签到满奖励通知            |
| 系统通知 | 邀请、角色互换、管理员公告、积分/钻石变动、账户变更等 |

### 10.2 WebSocket 消息格式

WebSocket 服务独立部署，连接 URL 为 `wss://<api-host>/ws`，完整协议如下。

#### 10.2.1 通用消息格式

```json
{
  "type": "notification",
  "data": {},
  "trace_id": "string",
  "sent_at": "2026-06-03T00:00:00Z"
}
```

#### 10.2.2 消息类型清单

| 方向 | type                    | 说明                 |
| ---- | ----------------------- | -------------------- |
| C→S  | `auth`                  | 鉴权帧               |
| S→C  | `auth_ok`               | 鉴权成功             |
| S→C  | `auth_failed`           | 鉴权失败             |
| C→S  | `ping`                  | 心跳                 |
| S→C  | `pong`                  | 心跳响应             |
| C→S  | `subscribe`             | 订阅组消息           |
| S→C  | `subscribed`            | 订阅确认             |
| S→C  | `notification`          | 通知消息             |
| S→C  | `order_status_changed`  | 订单状态变更         |
| S→C  | `wish_status_changed`   | 心愿状态变更         |
| S→C  | `love_point_changed`    | 积分变动             |
| S→C  | `diamond_changed`       | 钻石变动             |
| S→C  | `wish_fulfill_reminder` | 履约提醒             |
| S→C  | `sign_in_reminder`      | 签到提醒             |

#### 10.2.3 鉴权帧

客户端连接后 10 秒内必须发送鉴权帧：

```json
// C→S
{ "type": "auth", "token": "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...", "device_id": "device-uuid-xxxxx" }

// S→C 成功
{ "type": "auth_ok", "user_id": 10001, "groups": [1001, 1002], "heartbeat_interval": 30, "server_time": "2026-06-03T08:00:00Z" }

// S→C 失败
{ "type": "auth_failed", "code": "AUTH_INVALID_TOKEN", "message": "Token 无效或已过期" }
```

#### 10.2.4 心跳

```json
// C→S
{ "type": "ping", "timestamp": 1709452800000 }

// S→C
{ "type": "pong", "server_time": "2026-06-03T08:00:30Z" }
```

心跳间隔 30 秒；客户端超过 90 秒未发心跳，服务端主动断开。

#### 10.2.5 订阅协议

```json
// C→S
{ "type": "subscribe", "groups": [1001, 1002] }

// S→C
{ "type": "subscribed", "groups": [1001, 1002] }
```

连接鉴权后默认订阅用户所在的所有组，可通过 subscribe 动态调整。

#### 10.2.6 业务推送消息示例

订单状态变更：

```json
{
  "type": "order_status_changed",
  "data": {
    "order_id": 10001, "group_id": 1001,
    "status": "ACCEPTED", "old_status": "CREATED",
    "updated_by": 10002, "updated_at": "2026-06-03T08:30:00Z"
  },
  "trace_id": "...", "sent_at": "2026-06-03T08:30:00Z"
}
```

积分变动：

```json
{
  "type": "love_point_changed",
  "data": {
    "user_id": 10001, "group_id": 1001,
    "change_type": "EARN", "amount": 10,
    "available_after": 130, "frozen_after": 0
  },
  "trace_id": "...", "sent_at": "2026-06-03T19:00:00Z"
}
```

履约提醒（履约截止前 N 小时发送）：

```json
{
  "type": "wish_fulfill_reminder",
  "data": {
    "wish_id": 1001, "group_id": 1001, "name": "一起看电影",
    "fulfillment_due_at": "2026-06-06T10:00:00Z", "remaining_hours": 24
  },
  "trace_id": "...", "sent_at": "2026-06-05T10:00:00Z"
}
```

### 10.3 连接要求

- WebSocket 服务独立部署。
- 连接后 10 秒内必须完成鉴权。
- 心跳间隔 30 秒。
- 多实例场景使用 Redis 维护用户在线状态或连接路由。
- 离线消息写入通知表，用户重新上线后拉取。

### 10.4 管理后台端点概览

完整端点见 §13.3.12，此处只描述能力域。

#### 10.4.1 用户管理

- 列表 / 详情 / 禁用 / 解禁（写入审计日志）。
- 禁用后用户无法登录，订单/心愿保持原状。

#### 10.4.2 小组管理

- 列表 / 详情 / 组级配置覆盖（订单积分、容量、每日上限、超时时间）。
- 变更写入审计日志。

#### 10.4.3 全局配置

- 签到奖励、心愿质量奖励、订单默认积分、组等级表、风控开关等。
- 敏感配置变更需二次确认。
- 变更写入审计日志。

#### 10.4.4 经济修复

- 积分补偿 / 钻石补偿必须走流水（`type=ADJUST`），禁止直接改余额。
- 写入审计日志（操作人、操作原因、补偿前后余额）。
- 管理员单日钻石发放受 `admin_daily_diamond_limit` 限制。

#### 10.4.5 风控审核

- 待审核订单列表（`risk_status=SUSPECT/BLOCKED`）。
- 审核通过补发积分/经验，拒绝则 `REJECTED`。
- 审核结果写入审计日志。

#### 10.4.6 心愿质量评价

- 仅 `FINISHED` 状态可发放质量奖励。
- 钻石奖励走 `diamond_transactions`，同一心愿幂等。

#### 10.4.7 审计日志

- 记录所有管理员操作和系统关键动作。
- 支持按操作人、操作类型、目标、时间范围筛选。

### 10.5 推送通知（应用内 + 微信订阅消息 - 微信暂缓 V2.0）

#### 10.5.1 通知渠道

- **应用内实时通知**（V1.0 实现）：WebSocket 在线推送（详见 §10.2）。
- **微信订阅消息**（V2.0 暂缓）：用户离线时通过微信小程序订阅消息触达。MVP 阶段**仅做应用内通知**，微信推送在 V2.0 接入。
- **应用图标 Badge**（V2.0）：未读通知数同步到微信小程序桌面角标。

#### 10.5.2 V1.0 阶段：仅应用内通知

- 所有事件通知走 `notifications` 表 + WebSocket 推送（§10.2）。
- 不依赖微信订阅消息授权。
- 简化部署，不需维护 access_token 缓存。

#### 10.5.3 V2.0 阶段：微信订阅消息（暂缓实现）

微信小程序订阅消息机制（设计已定，V2.0 落地）：

- **一次性订阅**：用户主动点击"允许"后，可发送一次消息。用于：订单完成通知、心愿达成通知。
- **长期订阅**：仅开放给特定类目（如政务、医疗），普通商业类目需申请。本产品**暂未申请长期订阅**，所有通知都基于"一次性订阅"。
- **触发时机**：事件发生时检查用户是否授权；未授权则只写应用内通知表，不推送微信。

#### 10.5.4 V2.0 订阅消息模板（设计保留）

| 模板 ID（占位） | 标题             | 触发场景                              | 用户授权点               |
| --------------- | ---------------- | ------------------------------------- | ------------------------ |
| `TPL_ORDER_NEW` | 新的订单待接单    | 订单 CREATED                           | 第一次 Seller 角色激活时 |
| `TPL_ORDER_DONE`| 订单已完成        | 订单 CONFIRMED_COMPLETED               | 订单确认时                |
| `TPL_WISH_DONE` | 心愿已达成        | 心愿 FINISHED                          | 心愿反馈时                |
| `TPL_ROLE_SWAP` | 角色已互换        | 角色互换后                              | 角色互换时                |
| `TPL_SIGN_BONUS`| 双方签到奖励      | 双方都签到触发 full_team_bonus         | 首次签到时                |
| `TPL_DEADLINE`  | 履约即将到期      | 心愿 CLAIMED 剩余 24h                  | 选择心愿时                |

#### 10.5.5 V2.0 推送失败处理（设计保留）

- 微信推送失败（access_token 过期、用户拒收）不影响业务事务。
- 失败次数累加到 `notifications.push_fail_count`，超过 5 次标记为 `PUSH_DEAD`，只走应用内。
- 微信 access_token 集中管理，Redis 缓存，提前 5 分钟刷新。

#### 10.5.6 V2.0 推送频率限制（设计保留）

- 同一用户同类型通知 1 分钟内最多 1 条（防骚扰）。
- 同一用户单日最多 50 条微信推送（运营可调）。
- 夜间 22:00 - 次日 08:00 默认静默，只走应用内；用户可在设置中开启夜间推送。

### 10.6 埋点 / 事件分析需求

#### 10.6.1 埋点原则

- 所有"用户行为"事件必须埋点，独立于业务事件。
- 业务事件（订单/心愿）通过 event_log 写库；用户行为事件通过 SDK 上报到分析平台（如自建 ClickHouse / 神策 / GrowingIO）。
- 关键路径漏斗（注册→建组→首单→首心愿）必须 100% 埋点。
- 客户端缓存用户 ID 和 device_id，所有事件带 `user_id`、`device_id`、`group_id`、`app_version`、`os`。

#### 10.6.2 关键埋点事件

| 事件名                          | 触发时机                       | 关键属性                                   |
| ------------------------------- | ------------------------------ | ------------------------------------------ |
| `app_open`                      | App 启动                       | `is_first_open`, `app_version`              |
| `wechat_login_success`          | 微信登录成功                    | `is_new_user`, `from_invite`                |
| `group_created`                 | 创建组                         | `is_first_group`                            |
| `group_joined`                  | 加入组                         | `invite_source`                             |
| `food_created`                  | 创建菜品                       | `food_count`                                |
| `order_created`                 | 创建订单                       | `order_type`, `food_id`                     |
| `order_accepted`                | 接单                           | `wait_seconds`                              |
| `order_confirmed`               | 确认订单                       | `complete_seconds`, `point_grant_status`    |
| `wish_created`                  | 创建心愿                       | `initial_cost`                              |
| `wish_selected`                 | 选择心愿                       | `final_cost`, `frozen_after`                |
| `wish_finished`                 | 心愿完成                       | `fulfillment_hours`                         |
| `role_swapped`                  | 角色互换                       | `trigger_user_id`                           |
| `sign_in_done`                  | 签到                           | `consecutive_days`, `full_team`             |
| `footprint_created`             | 发布足迹                       | `related_type`                              |
| `push_received`                 | 收到推送                       | `template_id`, `tapped`                     |
| `push_tapped`                   | 点击推送                       | `template_id` → 跳转目标                   |
| `error_occurred`                | 客户端错误                     | `error_type`, `stack`                       |

#### 10.6.3 漏斗分析

- **首单漏斗**：`wechat_login_success` → `group_created/joined` → `food_created` → `order_created` → `order_confirmed`
- **心愿漏斗**：`order_confirmed`（≥3 次）→ `wish_created` → `wish_agreement_confirmed` → `wish_selected` → `wish_finished`
- **签到漏斗**：`app_open`（连续 7 日）→ `sign_in_done`（连续 7 日）

#### 10.6.4 性能与可用性埋点

- 接口 P95 延迟超阈值告警。
- 客户端冷启动时间 / 首屏渲染时间。
- WebSocket 断连重连次数。

#### 10.6.5 隐私合规

- 埋点禁止包含明文手机号、身份证、银行卡。
- 位置信息需用户授权；脱敏到城市级。
- 用户注销时（30 天后）联动删除分析平台数据。

## 12. 事件驱动架构

### 12.1 事件写入

- 应用层完成核心业务事务时，同事务写入 `event_log`。
- Worker 异步消费 `PENDING` 事件。
- 多 Worker 使用 `FOR UPDATE SKIP LOCKED` 或队列竞争消费。
- 事件处理成功标记 `DONE`，失败进入重试。
- 超过最大重试次数进入 `DEAD`，等待人工或补偿任务处理。

## 13. API 设计

### 13.1 通用约定

- 返回体统一包含 `code`、`message`、`data`、`trace_id`。
- 时间统一 UTC 存储，接口返回 ISO 8601。
- 写接口要求 `Idempotency-Key`。
- 列表优先使用 cursor 分页。
- 后台接口与用户接口权限隔离。

## 15. 安全、隐私与风控

### 15.1 安全要求

- 所有接口必须鉴权，除登录、公开静态资源和必要回调外。
- 所有组内资源必须校验成员关系。
- 管理后台必须启用强密码和二次验证。
- 上传文件必须校验大小、类型、后缀、MIME 和内容。
- 日志禁止写入敏感明文。

**上传安全（七牛云直传场景）**：

- **七牛 AccessKey / SecretKey**：通过环境变量或密钥管理服务（Vault / AWS Secrets Manager）注入，**严禁进代码库**。CI/CD 必须有密钥扫描检查。
- **upload token 颁发**：
  - 业务后端调用七牛 SDK 时**必须设置 `scope`** 限定可上传的 file_key 前缀。
  - token 必须包含 `mimeLimit` 和 `fsizeLimit`（七牛服务端二次校验）。
  - token 有效期不超过 1 小时；默认 3600 秒。
- **请求校验**：
  - `/api/uploads/token` 必须在鉴权后调用，记录 user_id。
  - 校验 `business_ref_type` 合法性。
  - 校验 size、content_type 在合法范围。
  - 限流：单用户每分钟最多 60 次 token 申请。
- **异步回调验证**：
  - 必须验证七牛回调的 `Authorization` 头签名。
  - 自定义变量 `x:user_id` 必须与七牛 token 中声明的一致。
- **删除鉴权**：`DELETE /api/uploads/{file_key}` 必须校验所有权（user_id 一致），防止越权删除。
- **日志脱敏**：
  - 七牛 token 禁止写入日志。
  - file_key 可记录（无敏感信息）。
- **监控告警**：
  - 单用户短时间大量 token 申请 → 告警。
  - 七牛 API 4xx/5xx 错误率异常 → 告警。
  - 异步回调签名验证失败 → 告警（可能伪造）。

### 15.2 隐私合规

- 最小化采集手机号、位置、图片等敏感数据。
- 提供注销、解绑、删除足迹、删除图片能力。
- 提供用户协议、隐私政策、儿童隐私条款。
- 地理位置默认可选。

### 15.3 风控

- 登录、注册、邀请、上传、下单、心愿选择、签到均需限流。
- 识别异常刷订单、刷积分、刷组经验、批量上传、恶意邀请。
- 每日爱心积分上限和每日组经验上限是全局防刷规则，所有订单类型都必须执行。
- 管理员补偿积分和发放钻石需保留审计。
- 钻石广告奖励预留反作弊校验。

### 15.4 客服与反馈入口

#### 15.4.1 客户端入口

- 我的页面 → 意见反馈。

- 客服处理的"补偿积分"必须经过 §15.4 工单流程，关联到 `audit_logs`。
- 禁止客服绕过管理员直接修改余额。

### 15.5 法务 / 平台合规

#### 15.5.1 微信小程序合规要求

- 主体类型：建议企业主体（个人主体功能受限）。
- 类目：工具 → 效率 / 社交 → 情侣；具体类目需在微信后台申请。
- 微信平台审核要点：
  - 必须有《用户协议》和《隐私政策》入口。
  - 必须有"注销账号"功能。
  - 收集用户位置需明确告知。
  - 不得向未成年人开放（年龄 ≥ 18 岁）。
  - 不得诱导分享到朋友圈。

#### 15.5.2 个人信息保护法 / 数据安全法合规

- **最小化采集**：仅采集业务所需字段；用户协议明确告知。
- **明示同意**：注册时勾选《用户协议》《隐私政策》。
- **数据本地化**：用户数据存储在境内（阿里云/腾讯云境内 region）。
- **数据出境**：不向境外提供数据；如未来需要需走安全评估。
- **儿童信息**：禁止 14 岁以下用户使用；14-18 岁需监护人同意。

#### 15.5.3 内容合规

- 菜品名 / 心愿名 / 足迹内容 / 反馈内容走内容安全审核。
- 关键词库：政治敏感词、色情、暴力、辱骂、广告。
- 命中后自动隐藏 + 通知发布人；连续命中 3 次人工审核。

#### 15.5.4 知识产权

- 用户上传图片默认视为"非商业用途授权"。
- 商业用途需另行签署。
- 心愿模板、菜谱模板可考虑开源协议。

#### 15.5.5 支付合规（钻石广告奖励）

- 看广告获取钻石：通过微信广告平台 / 字节穿山甲。

### 16.3 上传业务规则（七牛云直传）

#### 16.3.1 核心原则

- **业务后端不接收任何文件流**，仅生成并颁发**七牛云 upload token**。
- 前端使用 token **直接上传到七牛云的上传服务器**（不在业务后端转发）。
- 业务后端**不维护自建对象存储**，全部使用七牛云对象存储服务。
- 此设计**大幅减少业务后端的网络 I/O 和带宽压力**，让后端专注于业务逻辑。

#### 16.3.2 整体流程

```text
1. 客户端：POST /api/uploads/token
   请求: { filename, content_type, size, business_ref_type }
2. 后端：
   - 校验参数（大小/类型）
   - 生成 file_key（如 uploads/2026/06/03/abc123.jpg）
   - 调用七牛 SDK 生成 upload token
     （包含 bucket, scope=file_key, deadline, returnBody）
   - 写入 upload_files 表（PENDING 状态）
   - 返回 { upload_token, file_key, upload_host, expires_at }

3. 客户端：使用七牛 JS SDK 上传到 upload_host
   （form-data 方式，token + file）

4. 七牛返回：{ key, hash }

5. 客户端：POST /api/uploads/confirm
   请求: { file_key, hash, business_ref_type, business_ref_id }
6. 后端：
   - 校验 hash 与上传记录的 token 一致
   - 触发内容安全审核（异步）
   - 状态 PENDING → PASS / REJECTED

7. （可选）七牛异步回调：
   七牛 → POST /api/uploads/qiniu-callback
   后端更新 upload_files 状态
```

#### 16.3.3 七牛配置

| 配置项                  | 说明                                            | 维护方  |
| ----------------------- | ----------------------------------------------- | ------- |
| `QINIU_ACCESS_KEY`      | 七牛 AccessKey                                  | 运维    |
| `QINIU_SECRET_KEY`      | 七牛 SecretKey（**严禁进代码库**）              | 运维    |
| `QINIU_BUCKET`          | 存储桶名称                                      | 运维    |
| `QINIU_REGION`          | 存储区域（华东/华北/华南/北美等）                | 运维    |
| `QINIU_UPLOAD_HOST`     | 上传服务器域名（如 `upload.qiniup.com`）        | 运维    |
| `QINIU_CDN_DOMAIN`      | CDN 加速域名（公开访问）                        | 运维    |
| `QINIU_TOKEN_EXPIRE_S`  | token 有效期（默认 3600 秒 = 1 小时）           | 后端    |
| `QINIU_CALLBACK_URL`    | 异步回调 URL（如启用）                          | 运维    |

#### 16.3.4 文件约束

- **支持类型**：JPEG / PNG / GIF 三种 MIME（业务后端预校验）。
- **单文件大小**：最大 5 MB（5,242,880 字节）。
- **批量上传**：单次最多 9 个文件，总大小不超过 20 MB。
- **file_key 命名规则**：`{business_ref_type}/{yyyy}/{mm}/{dd}/{uuid}.{ext}`。
  - 例：`food/2026/06/03/abc123def456.jpg`
  - 例：`footprint/2026/06/03/xyz789.jpg`
  - 例：`checkin/2026/06/03/qwe456.jpg`
- **upload_token 有效期**：1 小时（默认）。
- **file_key 全局唯一**：通过 UUID 保证，避免冲突。

#### 16.3.5 七牛 Upload Token 内容

token 字符串（Base64 编码的 JSON）包含：

```json
{
  "scope": "may-store:uploads/food/2026/06/03/abc123.jpg",
  "deadline": 1748908800,
  "returnBody": "{\"key\":\"$(key)\",\"hash\":\"$(etag)\",\"size\":$(fsize),\"mimeType\":\"$(mimeType)\"}",
  "insertOnly": 1,
  "detectMime": 1,
  "mimeLimit": "image/jpeg;image/png;image/gif",
  "fsizeLimit": 5242880,
  "saveKey": "uploads/food/2026/06/03/abc123.jpg",
  "callbackUrl": "https://api.example.com/api/uploads/qiniu-callback",
  "callbackBody": "{\"file_key\":\"$(key)\",\"hash\":\"$(etag)\",\"user_id\":$(x:user_id)}",
  "callbackBodyType": "application/json"
}
```

关键字段说明：

- `scope`：限定只能上传到指定 key，防止越权。
- `deadline`：token 过期时间。
- `returnBody`：七牛返回给客户端的内容格式。
- `mimeLimit`：七牛服务端二次校验 MIME（**双保险**）。
- `fsizeLimit`：七牛服务端二次校验大小。
- `callbackUrl` / `callbackBody`：启用异步回调时使用。

#### 16.3.6 业务后端 /api/uploads/token 接口

请求体：

```json
{
  "filename": "photo.jpg",
  "content_type": "image/jpeg",
  "size": 1024000,
  "business_ref_type": "food"
}
```

| 字段                | 类型    | 必填 | 说明                                            |
| ------------------- | ------- | ---- | ----------------------------------------------- |
| `filename`          | string  | 是   | 原始文件名                                      |
| `content_type`      | string  | 是   | MIME 类型                                       |
| `size`              | integer | 是   | 文件大小（字节）                                |
| `business_ref_type` | string  | 是   | `food` / `footprint` / `checkin` / `avatar`      |

响应体：

```json
{
  "code": 0,
  "data": {
    "upload_token": "...",
    "file_key": "uploads/food/2026/06/03/abc123.jpg",
    "upload_host": "https://upload.qiniup.com",
    "expires_at": "2026-06-03T12:00:00Z"
  }
}
```

#### 16.3.7 前端上传示例（七牛 JS SDK）

```javascript
import * as qiniu from 'qiniu-js';

// 1. 申请 token
const { data: { upload_token, file_key, upload_host } } = await axios.post(
  '/api/uploads/token',
  {
    filename: file.name,
    content_type: file.type,
    size: file.size,
    business_ref_type: 'footprint'
  }
);

// 2. 配置七牛 SDK
const config = {
  useCdnDomain: true,
  region: qiniu.region.z0  // 华东
};

// 3. 上传到七牛
const observable = qiniu.upload(file, file_key, upload_token, {}, config);
const subscription = observable.subscribe({
  next(res) { /* progress */ },
  error(err) { /* handle */ },
  complete(res) { /* { key, hash } */ }
});
```

#### 16.3.8 内容安全审核

- **审核时机**：客户端调用 `/api/uploads/confirm` 后，异步触发。
- **审核方式**：
  - 方式 A：调用七牛云的图片审核 API（推荐）。
  - 方式 B：调用第三方审核服务（如阿里云内容安全、网易易盾）。
- **审核状态**：`PENDING` → `PASS` / `REJECTED`。
- **REJECTED 处理**：
  - 业务层将关联资源（菜品/足迹/打卡）标记为不可见。
  - 通知发布人。
  - 释放存储（调用七牛删除接口）。
  - 返回 `UPLOAD_CONTENT_REJECTED` 错误码。

#### 16.3.9 异步回调（可选）

如果启用七牛 `callbackUrl`：

- 七牛在文件成功上传到存储后，POST 到 `/api/uploads/qiniu-callback`。
- 后端更新 `upload_files.status = ACTIVE`。
- 携带 `user_id` 自定义变量，便于追踪。

#### 16.3.10 删除策略

- 用户主动删除：调用 `DELETE /api/uploads/{file_key}`。
- 后端：
  1. 校验所有权（`user_id` 必须匹配）。
  2. 调用七牛 `delete` API（基于 file_key）。
  3. 软删除 `upload_files` 记录（`status=DELETED`，`deleted_at`）。
  4. 关联业务资源（菜品/足迹/打卡）解除引用。

#### 16.3.11 安全要求

- 七牛 AccessKey / SecretKey 严禁进代码库，使用环境变量或密钥管理服务（如 Vault）。
- token 必须包含 `scope` 限定，防止越权上传。
- 服务端二次校验 MIME 和 size（前端可绕过）。
- 异步回调必须验证来源（七牛签名），防止伪造。
- 用户 ID 通过七牛自定义变量传递（`x:user_id`），禁止在 callback body 中明文传递敏感信息。

#### 16.3.12 错误码

| 错误码                     | 触发条件                       |
| -------------------------- | ------------------------------ |
| `UPLOAD_SIZE_EXCEEDED`     | size > 5MB                     |
| `UPLOAD_TYPE_NOT_ALLOWED`  | MIME 非 JPEG/PNG/GIF           |
| `UPLOAD_TOKEN_INVALID`     | 七牛 token 校验失败            |
| `UPLOAD_CONTENT_REJECTED`  | 内容安全审核未通过             |
| `UPLOAD_FILE_NOT_FOUND`    | file_key 在七牛不存在          |
| `UPLOAD_PERMISSION_DENIED` | 非文件所有者尝试删除           |

#### 16.3.13 监控与告警

- 七牛上传失败率（`status=FAILED` 比例）。
- 七牛 API 延迟 P95。
- 七牛 4xx/5xx 错误率。
- 内容审核 REJECTED 比例。
- upload_files 表 PENDING 状态积压数量。

#### 16.3.14 业务后端压力对比

| 指标           | 自建存储（经后端）| 七牛直传（当前）| 改善    |
| -------------- | ------------------ | ---------------- | ------- |

#### 17.5.3 常见故障处置

**数据库连接耗尽**

- 现象：API 5xx 突增，错误日志大量 `connection pool exhausted`。
- 处置：临时扩容 PgBouncer；kill 长事务；限流降级。
- 后续：优化连接池配置、限流阈值。

**事件消费积压**

- 现象：`event_log.status=PENDING` 持续增长。
- 处置：扩容 Worker 实例；检查失败日志修复 bug；必要时手工重放。
- 后续：分析积压原因，补充监控。

**Redis 故障**

- 现象：限流失效 / 在线状态错乱。
- 处置：Redis 主从切换；切到本地缓存兜底；只读降级。
- 后续：补 Redis 高可用 / 监控。

**微信 access_token 失效**

- 现象：推送失败率突增。
- 处置：手动刷新 access_token；检查定时任务。
- 后续：增加监控告警、提前刷新。

**风控误判**

- 现象：用户大量订单被标记 SUSPECT，积分未发。
- 处置：临时调宽规则；管理员批量审核。
- 后续：分析误判原因，调整规则权重。

### 17.6 数据迁移与回滚

#### 17.6.1 迁移原则

- **向后兼容**：新代码必须能读旧数据。
- **可回滚**：migration 脚本必须可逆（提供 down.sql）。
- **灰度执行**：大表变更先在影子表操作，再切换。
- **双写期**：必要时新旧表双写 1-2 周，确认一致后切读。
- **可观测**：migration 进度写入 `migration_log`，耗时/记录数实时可见。

#### 17.6.2 迁移工具与流程

- 工具：`sqlx migrate`（Rust 生态成熟方案）。
- 流程：
  1. 开发环境执行，验证 schema 和数据。
  2. staging 环境执行，shadow 流量对比。
  3. 生产环境选择低峰期执行（推荐 02:00-05:00）。
  4. 涉及大表（>1 亿行）的 DDL，使用 gh-ost / pg_repack 工具。
  5. 迁移后跑数据校验脚本，对比行数 / checksum。

#### 17.6.3 回滚预案

- **代码回滚**：保留最近 5 个版本，K8s 一键回滚。
- **配置回滚**：全局配置支持版本号，3 秒内回滚到上一版本。
- **数据回滚**：DDL 已执行的可逆操作通过 down.sql 回退；不可逆操作（如删字段）通过备份恢复。
- **影子表切换**：双写期可直接切回旧表。

#### 17.6.4 大表变更检查清单

- [ ] 评估锁表时间（< 1 秒可接受）。
- [ ] 准备 shadow 表 + 双写。
- [ ] 写好 down.sql 并演练。
- [ ] 准备数据校验脚本。
- [ ] 通知相关业务方。
- [ ] SRE 值班待命。

### 17.7 灰度策略细则

#### 17.7.1 灰度维度

- **按用户 ID 哈希**：5% / 30% / 100% 用户群。
- **按组 ID 哈希**：避免同一组用户分流到不同版本。
- **按地区 / 时区**：分省/分大区灰度。
- **按白名单**：内部测试组、种子用户先体验。

#### 17.7.2 灰度阶段

| 阶段 | 流量  | 持续时间 | 准入条件                       |
| ---- | ----- | -------- | ------------------------------ |
| 内部 | 0%    | 1-2 天   | 内部员工 + 种子用户            |
| 5%   | 5%    | 1 天     | 5xx 率 < 0.5%、无 P1 告警      |
| 30%  | 30%   | 2-3 天   | 业务指标无下降                  |
| 100% | 100%  | —        | 持续监控 24 小时无异常          |

#### 17.7.3 回滚决策

满足任一条件立即回滚：

- 5xx 错误率 > 1%（持续 5 分钟）。
- 核心接口 P95 延迟 > 2x 基线。
- 业务关键指标下降 > 10%（DAU、订单完成率）。
- 用户投诉量突增 > 50%。
- 监控告警 P0/P1 未消除。

#### 17.7.4 Feature Flag

- 使用统一 feature flag 服务（自建或 LaunchDarkly / Unleash）。
- 关键业务功能（积分发放、心愿完成、风控）必须可独立 flag 控制。
- flag 变更写入审计日志。

### 17.8 AB 测试框架

#### 17.8.1 目标

- 产品决策数据化：新功能上线前通过 AB 测试验证假设。
- 实验闭环：实验设计 → 流量分配 → 数据采集 → 显著性检验 → 决策。

#### 17.8.2 框架要素

- **实验配置**：实验名、变体（Control / Treatment A / B...）、流量分配、起止时间。
- **流量分配**：用户 ID 哈希到 [0, 10000)，落入区间即加入实验。
- **埋点**：每个变体独立埋点，属性包含 `experiment_id` 和 `variant`。
- **指标**：主指标（如心愿完成率）、辅助指标（DAU、留存）、护栏指标（投诉率）。
- **统计检验**：T 检验 / 卡方检验 / Bayesian 区间，置信度 ≥ 95%。

#### 17.8.3 常见实验场景

- 心愿选品引导文案。
- 签到奖励配置。
- 订单积分默认值。
- 推送文案优化。
- 做客订单限额。

#### 17.8.4 实验规范

- 同一时间一个用户最多参与 3 个实验，避免污染。
- 互斥实验：相同模块的实验用同一层（layer）互斥。
- 强制正交：不同层之间随机正交。
- 实验结束必须清理代码、配置、埋点。

#### 17.8.5 决策流程

- 显著性达成 + 业务正向 → 全量。
- 显著性达成 + 业务负向 → 回滚。
- 无显著性 → 延长实验或放弃。
- 显著性达成但护栏指标恶化 → 不上线，重新设计。

## 21. 当前已确认决策

1. 产品只面向固定双人组。
2. 资产合并为个人爱心积分 `love_point` 和组钻石 `diamond`。
3. 心愿模块按“用户创建、双方协商积分和履约期限、双方线上确认、进入心愿池、发起人攒积分选择、对方自然人履约、发起人打卡反馈、管理员按质量发放额外钻石”重构。
4. 做客用户需要长期账号，且可拥有自己的组。
5. 暂不做钻石充值，仅预留看广告获取钻石。
6. 无公开广场，内容仅组内显示。
7. 后端技术选型保持 Rust + PostgreSQL。
8. 10 万用户目标指注册用户。
9. 用户侧取消订单积分配置，所有配置相关能力全部交由管理员后台维护。
10. 做客用户通过邀请链接访问主人家厨房，看菜单、下单、备注标记；订单列表同时展示自己组订单和做客订单。
11. 做客订单由主人家完成后可给主人家 Seller 发放爱心积分，但必须接入防刷积分风控。
12. 防刷规则覆盖所有订单：用户每日爱心积分有上限，小组每日经验有上限，超出后订单完成但不再增加积分或经验。
13. 完成订单同样增加组经验并推动组升级，升级经验、每日经验上限和等级加成由管理员后台配置。
14. 心愿履约人与自然人用户 ID 绑定，和当前角色无关；逾期退还积分并记录履约数据，组内可查看履约率。
15. 用户退出组前必须结清未完结心愿、履约责任、冻结积分和相关补偿。

## 22. 关键实现提醒

- 心愿打卡反馈完成前不要正式扣除爱心积分，只冻结。
- 履约逾期、关闭都必须处理冻结积分退还。
- 角色切换只改变当前组角色映射，不修改历史记录。
- 已选择心愿的发起人和履约人永远按自然人用户 ID 绑定，角色切换不改变责任。
- Buyer 不通过订单获得爱心积分，这是轮换机制的核心约束。
- 每日积分/经验上限是订单奖励发放的硬约束，超上限订单照常完成但不发奖励。
- 同一组最多 2 名正式成员，这是权限、数据隔离和 UI 设计的基础假设。
- 所有经济、审核、角色互换操作都必须可审计、可追踪、可补偿。

### 24.1 订单明细（order_items）

#### 24.1.1 业务目标

FSD §6 订单系统当前 `orders.food_id` 仅支持单菜品。实际场景中"做一桌菜"是多菜品的复合订单，必须支持订单明细。

#### 24.1.2 数据模型

`order_items` 表：

| 字段          | 类型      | 说明                          |
| ------------- | --------- | ----------------------------- |
| `id`          | BIGSERIAL | 明细 ID                       |
| `order_id`    | BIGINT    | 关联订单                      |
| `food_id`     | BIGINT    | 关联菜品                      |
| `quantity`    | INT       | 数量（默认 1）                |
| `price`       | NUMERIC   | 单价快照                      |
| `snapshot_json` | JSONB   | 菜品快照（名称/图片/步骤）    |
| `created_at`  | TIMESTAMP | 创建时间                      |

`orders` 表新增 `item_count` 字段（冗余，便于快速查询）。

#### 24.1.3 业务规则

- 一个订单 1~N 个明细项，每个明细对应一个菜品。
- 创建订单时所有明细项必须属于同一 group。
- 状态机与订单级保持一致（订单取消时所有明细级联取消）。
- 积分/经验仍按订单级计算（一次订单 = 一次奖励机会），不按明细重复发放。
- 删除菜品不能级联删除已使用该菜品的订单明细（明细保留 snapshot）。

#### 24.1.4 API

- 创建订单请求体支持 `items: [{ food_id, quantity }]`（替代单 `food_id`）。
- 订单详情响应包含 `items: [...]` 明细列表。

### 24.2 订单状态历史（order_status_history）

#### 24.2.1 业务目标

每次订单状态变更留痕，便于审计、追踪订单生命周期、客诉处理。

#### 24.2.2 数据模型

| 字段           | 类型      | 说明                                |
| -------------- | --------- | ----------------------------------- |
| `id`           | BIGSERIAL | 记录 ID                             |
| `order_id`     | BIGINT    | 关联订单                            |
| `from_status`  | ENUM      | 变更前状态（可空，新建时为空）      |
| `to_status`    | ENUM      | 变更后状态                          |
| `changed_by`   | BIGINT    | 触发人（用户/管理员/System）         |
| `remark`       | VARCHAR   | 备注                                |
| `changed_at`   | TIMESTAMP | 变更时间                            |

#### 24.2.3 业务规则

- 每次状态机迁移必须**同事务**写入 `order_status_history`。
- 与 `audit_logs` 互补：`order_status_history` 是状态迁移流水，`audit_logs` 是后台操作流水。
- 不允许删除历史记录。
- 超过 1 年的历史记录可归档（备份后删除）。

#### 24.2.4 API

- 订单详情响应可选返回 `status_history: [...]`。
- 管理员可在后台查看完整状态历史。

### 24.3 订单评分（order_ratings）

#### 24.3.1 业务目标

订单完成后，Buyer 对 Seller 履约质量评分，影响 Seller 后续可获得的"评分调整积分"，是服务质量的反馈机制。

#### 24.3.2 数据模型

| 字段           | 类型      | 说明                          |
| -------------- | --------- | ----------------------------- |
| `rating_id`    | BIGSERIAL | 评分 ID                       |
| `order_id`     | BIGINT    | 关联订单（唯一）              |
| `rater_user_id` | BIGINT   | 评分人（Buyer）               |
| `target_user_id` | BIGINT  | 被评分人（Seller）            |
| `delta`        | INT       | 积分调整（可正可负）          |
| `remark`       | VARCHAR   | 评分备注                      |
| `created_at`   | TIMESTAMP | 评分时间                      |

#### 24.3.3 业务规则

- 仅 Buyer 可评分自己创建的本组订单。
- 仅 `CONFIRMED_COMPLETED` 状态订单可评分。
- 每个订单只能评一次（`UNIQUE(order_id)`）。
- `delta` 范围由管理员配置（默认 -10 ~ +10）。
- 评分后通过 `love_point_transactions` 调整 Seller 的可用积分：
  - `delta > 0` → `EARN` 流水
  - `delta < 0` → `ADJUST` 流水
- 评分不在每日积分上限内。
- 评分不影响组经验和组等级。

#### 24.3.4 API

- `POST /api/orders/{order_id}/rating` - 提交评分
- `GET /api/orders/{order_id}/rating` - 获取评分详情

### 24.11 做客邀请（guest_invitations）

> FSD §4.2 已定义"组邀请"。做客场景需要一个**额外**的"做客邀请"机制（不同于加入组的邀请）。

#### 24.11.1 与 group_invites 的区别

| 维度         | group_invites           | guest_invitations            |
| ------------ | ----------------------- | ---------------------------- |
| 目的         | 加入组成为正式成员      | 受邀访问主人家厨房点菜      |
| 关系         | 长期（成为 Buyer/Seller）| 临时（做客单次）             |
| 数量限制     | 1 次（加入即满 2 人）   | 多次（`max_uses`）            |
| 失效         | 加入后或过期            | 用完、过期或主人家主动撤销   |
| 关联订单     | 无                      | 关联 `orders.guest_invite_id`|

#### 24.11.2 数据模型

| 字段            | 类型      | 说明                          |
| --------------- | --------- | ----------------------------- |
| `id`            | BIGSERIAL | 邀请 ID                       |
| `group_id`      | BIGINT    | 所属主人家组                  |
| `invite_code`   | VARCHAR   | 邀请码（unique）              |
| `created_by`    | BIGINT    | 创建人（主人家 Seller）        |
| `max_uses`      | INT       | 最大使用次数（默认 1）        |
| `used_count`    | INT       | 已使用次数                    |
| `expires_at`    | TIMESTAMP | 失效时间                      |
| `status`        | ENUM      | `ACTIVE` / `EXPIRED` / `REVOKED` |
| `created_at`    | TIMESTAMP | 创建时间                      |

#### 24.11.3 业务规则

- 仅主人家 Seller 可创建做客邀请（`POST /api/groups/{group_id}/guest-invitations`）。
- 同一邀请链接默认最多 1 次使用。
- 同一做客用户对同一主人家每日可计分做客订单 ≤ 1 单（防刷）。
- 主人家可主动撤销邀请（`POST /api/groups/{group_id}/guest-invitations/{id}/revoke`）。
- 邀请失效不删除历史记录（审计）。

#### 24.11.4 API

- `POST /api/groups/{group_id}/guest-invitations` - 创建
- `GET /api/kitchens/invitations/{invite_code}` - 受邀人查看邀请详情
- `POST /api/admin/groups/{group_id}/guest-invitations/{id}/revoke` - 撤销

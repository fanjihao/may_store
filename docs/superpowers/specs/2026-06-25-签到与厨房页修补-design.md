# 签到页 + 厨房页 4 项修补 设计

> **状态**：待审（4 段方案已通过用户口头批准，待 spec 文档过审）
> **作用域**：may_store 后端 + wx-store 前端
> **不涉及**：数据库 schema 变更（v3.sql 不动）
> **提交后用户能做什么**（一句话）：签到页看得到"昨天是否签过"；签到成功后厨房页钻石自动跳；厨房页能改组名、能新增 / 编辑 / 删除菜品。

---

## 1. 背景与目标

**用户原始诉求**（人话版，按 4 件事列）：

| # | 用户原话 | 产品目标 |
|---|---|---|
| 1 | 「签到页进入之后，未签到时看不到已经签到几天了，例如昨天已签到，今天进入签到页面看不到昨天是否签到，必须签到之后才能看到」 | 今天没签时，进度条第 1 格（昨天对应的）应点亮；"连续 X 天 / 累计 Y 天"数字要正确 |
| 2 | 「签到成功希望发送 socket，前端接收到之后更新 group 信息，避免出现签到后，stash 页面钻石未更新的情况」 | 签到成功后，组里所有在线客户端的厨房页自动刷新组信息（钻石 / 经验） |
| 3 | 「stash 页面的编辑 group 接口未补充」 | 厨房页改组名按钮可点，能成功保存 |
| 4 | 「添加菜品未完成」（后续追加：「菜品编辑删除也要完成」） | 厨房页"+"号新增、笔图标编辑、垃圾桶删除 三件套都能跑通 |

**当前现状（基线）**：
- 后端 `src/api/sign_in/routes.rs::sign_in_status`：用 `LEFT JOIN ... AND sr.sign_date = $2` 只取"今天"那一条；今天没签就返回 `consecutive_days = 0` —— **这是 #1 的根因**
- 后端 `src/application/sign_in_service.rs::daily_checkin`：写完钻石后**不广播 ws** —— **这是 #2 的根因**
- 后端 `src/api/groups/routes.rs`：只有 `PATCH /api/groups/{group_id}/point-config`（改积分配置），**没有改组名的 PATCH** —— **这是 #3 的根因**
- 前端 `src/pages/stash/stash.vue::addNewFood` / `editFood`：都弹"暂未开放"toast，没做 `uni.navigateTo` —— **这是 #4 的根因**
- 前端 `src/pages/stash/stash.vue::confirmDelete`：已调 `apiDeleteFood`，**但没 try/catch**，删失败用户看不到任何提示 —— **加固目标**

**不涉及**：
- 数据库 schema（`src/v3.sql` 不动）—— group_name、sign_in_records、association_groups.diamond 等字段早就在了
- admin 后台（multi-admin 项目不在本次范围）

## 2. 设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| #1 连续天数算法放哪 | 后端（sign_in_status 内） | 前端逻辑 0 改动；字段语义不变；测试也好做 |
| #1 连续天数规则 | 看最近一条签到记录：今天 / 昨天 → 保留 streak；更早 → 0 | 与产品"streak 还没断"直觉一致；不返历史列表给前端 |
| #2 ws 消息类型 | **新增** `group_diamond_change`（不复用 `group_member_change`） | 用户明确选择"单独发一个"；与"组队变动"语义不同，混用会乱 |
| #2 推送时机 | 事务提交之后、HTTP 200 之前 | 不影响签到结果；离线 / 失败静默丢弃 |
| #2 推送失败影响 | 不影响签到返回 200 | 兜底靠下次进入页面重新拉 |
| #3 改组名端点 | `PATCH /api/groups/{group_id}/name`（专用） | 用户明确选择"专用"；语义最清晰 |
| #3 改组名权限 | 组内任何 ACTIVE 成员 | 用户明确选择 |
| #3 改组名要不要广播 ws | **不广播** | 改组名是低频动作，对方下次进入下拉刷新即可；减少不必要推送 |
| #4 新增 / 编辑 | 共用 `/pages/newfood/newfood` 页 | 页面已支持 `editInfo` prop；stash.vue 设 storage + navigate 即可 |
| #4 删除失败处理 | stash.vue 的 `confirmDelete` 加 try/catch + 错误 toast | 当前裸 promise，失败用户无感知 |
| #4 客人视角（visitMode） | 三件套全部继续屏蔽 | 沿用现有 `if (visitMode.value) return` 逻辑 |
| #4 REJECTED 重新申请 | 沿用 newfood 组件现有逻辑 | 不重新设计 |

## 4. 后端改动

### 4.1 `#1` 修复 sign_in_status 的连续天数算法

**文件**：`src/api/sign_in/routes.rs::sign_in_status`

**改法**：
- 在原 `LEFT JOIN sign_in_records sr ON ... AND sr.sign_date = $2` 之外，**额外查一次**：
  ```sql
  SELECT sign_date, consecutive_days FROM sign_in_records
  WHERE group_id = $1 AND user_id = $2
  ORDER BY sign_date DESC LIMIT 1
  ```
- 用这次查到的 `last_sign_date` 决定 `consecutive_days`：
  - 今天有签到（sr_today 存在）→ 用今天的 `consecutive_days`
  - 今天没签、但 `last_sign_date == 今天 - 1 天` → 用最近这条的 `consecutive_days`（streak 还在）
  - 今天没签、且 `last_sign_date < 今天 - 1 天` → 0
  - 从没签过（last_sign_date IS NULL）→ 0

**今天签到且 streak 已断但被复活**（中间断过）的情况：`daily_checkin` 内部已经处理（重置为 1），不在这条修复范围内。

**测试**：
- 单元测试（`#[cfg(test)]` 加一个 `case`）：模拟三种情况（今天签了 / 昨天签了今天没签 / 3 天前签的），断言返回的 `consecutive_days`

### 4.2 `#2` 新增 ws 消息类型 + 推送

**文件 A**：`src/api/ws/messages.rs`
- 新增 `WsGroupDiamondChangeData` 结构体（字段：`groupId / userId / diamond / exp / level / consecutiveDays / reason`，`reason` 这次固定 `"sign_in"`）
- 在 `WsEnvelope` 加构造方法 `group_diamond_change(&WsGroupDiamondChangeData) -> Self`
- `reason` 用 `#[serde(rename_all = "snake_case")]` 风格序列化

**文件 B**：新建 `src/api/sign_in/broadcast.rs`
- 新增 `push_group_diamond_change_notice(db, group_id, user_id, reason)` 函数（与 `push_group_member_change_notice` 风格保持一致）：
  - 拿 group 最新信息（`association_groups` 一行）
  - 拿 user 累计签到天数（`sign_in_records` COUNT）
  - 构造 `WsGroupDiamondChangeData`，调 `WsEnvelope::group_diamond_change` → JSON
  - 按 group_id 反查所有 ACTIVE 成员（沿用 `push_group_member_change_notice` 的 SQL 模式）
  - 逐个调 `manager.send_to_user(target_id, &json)`
  - 失败 / 离线静默丢弃，**不抛错**

**文件 C**：`src/application/sign_in_service.rs::daily_checkin`
- 在 `daily_checkin` 拿到新的 `diamond_reward` / `consecutive_days` 之后、返回之前，调一次 `push_group_diamond_change_notice`（如果上一步 `add_diamond` 之类的 SQL 还没提交，需要在事务边界内/外协调 —— 简单做法：把推送放在 commit 之后；如果 commit 失败则不推送）

### 4.3 `#3` 新增改组名端点

**文件**：`src/api/groups/routes.rs`

**路由**：
```rust
cfg.service(
    web::resource("/api/groups/{group_id}/name")
        .guard(group_id_is_numeric())
        .route(web::patch().to(update_group_name)),
);
```

**handler `update_group_name`**：
- 入参：`{ "name": "新名字" }`
- 鉴权：复用 `RequireGroup`（已现成的）
- 服务端校验：1-10 位中英文 / 数字 / 下划线（与前端正则一致）
- 校验失败 → 400 + 文案
- 校验通过 → `UPDATE association_groups SET group_name = $1, updated_at = NOW() WHERE group_id = $2`
- 返回 200 + 新组名

**v3.sql 不动**（`group_name` 字段早就在了）

**OpenAPI 标注**（`#[utoipa::path]`）按现有风格写齐

### 4.4 后端 `v3.sql` 变更

**无**。`v3.sql` **不动**。所有改动复用现有表和字段。

## 6. 错误处理 / 边界 / 兜底

| 场景 | 表现 |
|---|---|
| 签到 ws 推送失败 / 对方离线 | 我这边签到照常 200；对方下次进厨房页下拉刷新拿新值 |
| 改组名校验失败（名字含特殊字符 / 11 位） | 前端正则挡 → 后端兜底再挡一次 → 400 错误 |
| 改组名网络错 | 前端弹错误 toast，弹窗不关 |
| 删除网络错 / 没权限 | 弹错误 toast，弹窗关，菜还在 |
| 编辑菜品 PATCH 失败 | 留在编辑页，弹错误（newfood 组件已有逻辑） |
| 客人视角 | 三件套全部继续屏蔽（沿用现有 `visitMode` 判断） |
| 用户从没签过 | `consecutive_days = 0`、7 格全灰、按钮"立即签到" |

## 7. 验收标准

**#1 签到页进度条**：
- 测试用户：昨天已签到（连续 1 天），今天打开签到页
  - 顶部数字"连续签到 1 天" / "累计签到 N 天"显示正确
  - 7 格中第 1 格亮
  - 按钮"立即签到"
  - 点按钮 → 第 2 格亮，顶部变成"连续签到 2 天"
- 测试用户：3 天没签到，今天打开签到页
  - 顶部数字"连续签到 0 天"
  - 7 格全灰
  - 按钮"立即签到"

**#2 签到后实时推送**：
- A 设备厨房页打开（账号甲）→ B 设备厨房页打开（账号乙）→ 乙签到 → A 设备钻石 / 经验数字**几秒内**自动跳到新值
- 推送失败 / 离线：签到 200，钻石变动消息丢失，下次进入厨房页数字是对的

**#3 改组名**：
- 厨房页点改组名图标 → 弹窗 → 输入新名字 → 确认 → 弹"修改成功" → 当前页组名变新名字
- 关掉再开厨房页 → 还是新名字（DB 持久化）
- 错误：清空 / 11 位 / 特殊字符 → 提示对应错误

**#4 菜品三件套**：
- "+" → 进新增页 → 填好 → 保存 → 回厨房页看到新菜
- 笔图标 → 进编辑页（旧值预填）→ 改 → 保存 → 回厨房页那道菜显示新值
- 垃圾桶 → 弹确认 → 确认 → 弹"删除成功" → 那道菜消失
- 删除失败：弹错误，菜还在

## 9. 风险 / 限制

- **后端 `daily_checkin` 推送与事务边界**：如果事务在推送之前 commit，签到成功但推送失败 → 用户体验正常（兜底靠下次拉取）；如果 commit 在推送之后 → 极端情况下推送发出但 commit 失败，对方收到假消息。**做法：commit 在前，推送在后**（最常见的模式，对方看到的是稍早一点点的"应该对"的状态，差异可忽略）。
- **wx-store 端 ws 监听位置**：如果厨房页有多个入口（客人 / 主用户），监听要在每个入口挂上。**这次只接主用户，客人视角后面补**。
- **改组名不广播**：对方设备当下看不到新组名，**接受这个延迟**（产品上合理）。

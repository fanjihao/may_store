# Implementation Plan - Footprint Module V1.0 (MVP)

## Context

The "Footprint" (足迹) module is a new MVP feature designed to enhance user engagement and retention by allowing users in a group (typically pairs) to document shared experiences, such as dining together. This module integrates with existing systems (orders, check-ins, groups) and introduces a new gamification currency called "Diamonds".

## Requirements & Constraints

- **Target Audience**: Users already bound in a `group` (2-person group support in V1.0).
- **Core Features**:
  - Data overview (together dining days, total feedings, streaks, total records).
  - Story sharing (categories: Dry Rice Daily, Feeding Diary, Anniversaries).
  - Automatic draft generation from completed orders.
  - Diamond system (earning through check-ins, records, and sharing; spending on capacity expansion).
  - Engagement tools: Likes, comments, and poster generation.
- **Constraints**:
  - Diamonds are separate from Heart points.
  - Only group members can access and interact within their group's footprint.
  - Capacity limits per category (starting at 50 records).

## Proposed Changes

### 1. Database Schema (`sqlx`/PostgreSQL)

New tables to be created:

- `user_diamond`: Stores user balance and lifetime stats.
- `diamond_flow`: Audit log for all diamond transactions.
- `record_group`: Category management for stories (e.g., "Dry Rice Daily").
- `user_record`: The actual story/footprint entries (including drafts).
- `record_comment`: User comments on records.
- `record_like`: User likes on records.

### 2. Backend Module: `src/footprint/`

- **`models.rs`**: Define DB entities and API request/response DTOs.
- **`service.rs`**:
  - `get_overview_data`: Aggregates statistics for the group dashboard.
  - `award_diamonds`: Atomic function to update balance and record flow.
  - `create_draft_from_order`: Hook to be called when an order is finished.
  - `submit_record`: Handles new record creation and diamond rewards.
  - `expand_capacity`: Deducts diamonds to increase category limits.
- **`routes.rs`**: Implementation of the 14+ endpoints defined in the requirement doc.
- **`mod.rs`**: Module exports and route registration.

### 3. Integration Points

- **`src/routes.rs`**: Register the new footprint routes.
- **`src/orders/service.rs`**: Add a hook in the order completion logic to trigger `create_draft_from_order`.
- **`src/users/service/sign.rs`**: Integrate diamond rewards into the existing daily check-in logic.
- **`src/users/routes/group.rs`**: Reuse group info fetching for the footprint dashboard.

### 4. Critical Files

- `src/routes.rs` (Central route registry)
- `src/orders/service.rs` (Order lifecycle hooks)
- `src/users/service/sign.rs` (Check-in logic)
- `src/footprint/mod.rs`, `service.rs`, `models.rs`, `routes.rs` (New module)

## Verification Plan

### Automated Testing

- **Unit Tests**:
  - Diamond balance arithmetic and daily limits.
  - "Together days" calculation logic (date deduplication).
- **Integration Tests**:
  - Verify `POST /api/orders/{id}/status` triggers record draft creation.
  - Verify `POST /api/sign` grants the correct number of diamonds.

### Manual Verification

1. **Entry Check**: Access footprint API without a group (expect 403/Error) and with a group (expect 200).
2. **End-to-End Flow**:
    - Complete an order -> Check for new draft.
    - Convert draft to record -> Check diamond balance increase.
    - Reach 50 records -> Attempt to add record (expect failure) -> Use diamonds to expand -> Add record (expect success).
3. **Audit**: Verify `diamond_flow` entries match all balance changes.
